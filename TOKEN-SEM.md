| Параметр | Значение |
|---|---|

## Главная мысль

Доверие к токену нельзя создать обещаниями — только отсутствием
возможностей. Поэтому в контракте нет ни одной функции, которая давала бы
кому-либо власть над чужими токенами. Не «мы обещаем не замораживать
переводы», а «заморозить нечем»: функции `pause` не существует.

Что отсутствует физически:

| Рычаг | Что позволял бы | Почему нет |
|---|---|---|
| `mint` | допечатать токены и обесценить остальные | предложение задаётся один раз в конструкторе |
| `owner` / роли | единолично решать судьбу токена | нет адреса, обладающего властью |
| `pause` | заморозить чужие переводы | перевод нельзя остановить |
| `blacklist` | запретить конкретному адресу продавать | перевод нельзя запретить |
| налог на перевод | скрыто изымать долю | переводится ровно `amount` |
| `upgrade` / прокси | подменить код по тому же адресу | код неизменяем |
| `delegatecall` | исполнять чужую логику | нет |
| `selfdestruct` | уничтожить контракт вместе с балансами | нет |
| `burnFrom` | сжечь чужие токены | сжигаются только свои |

Единственное, что может владелец, — распорядиться своими токенами. Ровно то
же может любой держатель.

## Что есть

- Обычный ERC-20: `transfer`, `approve`, `transferFrom`, `balanceOf`,
  `allowance`, `totalSupply`, `name`, `symbol`, `decimals`.
- `burn` — сжечь **свои** токены. Предложение может только уменьшаться.
- EIP-2612 `permit` — одобрить расход одной подписью, без отдельной
  транзакции `approve`. Это удобство, а не власть: permit лишь выставляет
  разрешение, которое владелец и так может выдать вручную.

`approve` ведёт себя строго по стандарту. Был соблазн запретить смену
ненулевого разрешения, чтобы закрыть известную гонку `approve`/`transferFrom`,
но такой запрет отклоняется от ERC-20 и ломает совместимость: агрегаторы,
боты и кошельки вызывают `approve` напрямую и не ждут отказа. Токен, на
котором спотыкается привычный инструмент, теряет доверие быстрее, чем
приобретает от защиты от редкой гонки.

## Как проверено

91 проверка на настоящем байткоде в локальной EVM — контракт разворачивается,
вызывается, результаты сверяются:

```bash
npm test                          # все 246 проверок проекта
node scripts/test-token.mjs       # 61 — сам токен
node scripts/test-token-dex.mjs   # 30 — работа в пулах
```

Сам токен (61):

- метаданные, предложение, баланс получателя;
- переводы, отказ при нехватке баланса и на нулевой адрес;
- `approve` / `transferFrom`, включая безлимитное разрешение;
- **отсутствие 14 административных функций** — проверяется по байткоду: если
  селектора нет, функции не существует;
- **изменяющих функций ровно пять** и все ожидаемые — появление шестой уронит
  тест;
- в исходнике нет `delegatecall`, `selfdestruct`, `assembly`, наследования;
- `permit`: валидная подпись, отказ просроченной, защита от повтора, отказ
  чужой подписи;
- инвариант: сумма всех балансов равна предложению.

Работа в пулах (30) — то, что не видно по самому токену:

- пара V2 SEM/WBNB: добавление ликвидности, обмены в обе стороны, вывод;
- пул V3: создание, ликвидность в диапазоне ±2%, своп;
- проверка, что налога нет: сумма балансов до и после перевода совпадает.

Этот набор ловит нестандартное поведение (налог, блокировки, придирки к
`transferFrom`), которое сломало бы свопы у пользователя.

## Что осталось сделать

1. **Решить параметры выпуска.** Сейчас по умолчанию 1 млрд SEM на адрес
   деплоера. Вопрос к отцу: сколько и кому. Обычная практика — разделить на

2. **Деплой.** Нужен ключ (`DEPLOYER_KEY`) и примерно 0.01 BNB на газ:

   ```bash
   node scripts/deploy.mjs --dry-run --with-token   # посмотреть, без трат
   DEPLOYER_KEY=0x... node scripts/deploy.mjs --with-token
   ```

3. **Верификация на BscScan** — чтобы исходник был виден публично. Это важнее
   любого текста в README: человек может прочитать код сам.
4. **Отозвать у деплоера права**, если где-то останутся: у этого контракта их
   нет, но у будущих может понадобиться.
5. **Пул ликвидности.** Токен сам по себе не торгуется — нужна пара. Для
   начала достаточно V2 SEM/WBNB.
6. **Аудит или публичный разбор.** Для «максимума доверия» независимый
   просмотр стоит дороже, чем любые обещания. Контракт маленький (198 строк),
   его реально прочитать целиком.

## Что сказать отцу про доверие

Честно: контракт без администратора — сильная сторона, но не гарантия роста
цены. Он снимает риск того, что создатель заберёт средства или заморозит
торговлю. Он не снимает риск того, что токен никому не нужен.

Доверие складывается из трёх вещей, и код — только первая:

1. **Код без рычагов** — сделано.
2. **Публичная верификация на BscScan** — чтобы код можно было прочитать.
3. **Ликвидность и последовательность** — пул с реальными деньгами и время без
   сюрпризов. Это то, что нельзя написать в контракте.

Обещать «максимум доверия» одной лишь архитектурой было бы неправдой.
Архитектура убирает худший класс рисков — тот, где создатель может навредить.
Остальное набирается делами, а не строками кода.

## Мелочи, которые стоит знать

- `totalSupply` не `immutable`: `burn` его уменьшает. Увеличить нечем.
- `MINIMUM_LIQUIDITY` (1000) навсегда блокируется в паре при первом
  добавлении ликвидности — поэтому пара не может опустеть до нуля. Это норма,
  а не дефект.
- При проверке `permit` важно передавать `prehash: false`: дайджест уже прошёл
  `keccak256`, повторное хеширование даёт неверную подпись.
- Тесты не требуют Foundry и Hardhat — только `solc` и `@ethereumjs/vm`.
