# Запертая позиция: ошибка первого минта в новом диапазоне тиков

**Статус: исправлено и передеплоено 2026-11-26.**

Дефект был найден и воспроизведён в Foundry на пуле `0x3688726E5811E766A0cA014dCEC24622c0d02583`.
Правка внесена в `contracts/SementsulV3.sol`, к ней 6 регрессионных тестов в
`test/StuckPosition.t.sol` (три из них падают на старом коде). Новые контракты
развёрнуты и верифицированы:

| | адрес |
|---|---|
| Фабрика V3 | `0xc0b597bee57bba0aae2ce9e73e83217331a24dd9` |
| Роутер V3 | `0xf98b7f4effb34dae1f785010ecf71ff796e7fdd1` |
| Пул WBNB/USDT 0.05% | `0x37c7702B589c69D1e4f4ad32E19f372ED6780278` |
| Старый пул (не использовать) | `0x3688726E5811E766A0cA014dCEC24622c0d02583` |

Работа исправления проверена на живом пуле полным циклом: своп начислил комиссию,
первый `collect` запустил вестинг, второй `collect` после 1150 блоков выплатил
0.0005 USDT и 0.0000042 WBNB реальными токенами.

**Последствие дефекта:** позиция перестаёт отвечать на `collect` и `burn` — деньги
недоступны, пока глобальная комиссия не вырастет вдвое (см. «Насколько это навсегда»).
**Масштаб:** только те LP, кто первым инициализирует новый диапазон тиков в пуле, где уже
накоплены комиссии.

## В чём ошибка

В `SementsulV3Pool._modifyPosition` комиссия считается **до** обновления тиков, и это правильно
для уже существующей позиции. Но при первом минте в новый диапазон `_feeGrowthInside`
читает ещё не инициализированные тики (у них `feeGrowthOutside = 0`) и возвращает **весь
`feeGrowthGlobal`**, хотя позиция не заработала ни одной комиссии.

Затем это значение безусловно записывается в позицию:

```solidity
// contracts/SementsulV3.sol:1106-1107 — выполняется всегда
position.feeGrowthInside0LastX128 = inside0;
position.feeGrowthInside1LastX128 = inside1;
```

А `_updateTick` (строки 1136-1145) сразу после этого ставит нижнему тику
`feeGrowthOutside = feeGrowthGlobal`. В итоге:

| момент | `inside0` | сохранённое `last` |
|---|---|---|
| минт | `global - 0 - 0` = **global** | **global** |
| следующий сбор | `global_now - global_mint - 0` ≈ 0 | global |

И вычитание в строке 1040 уходит в минус:

```solidity
FullMath.mulDiv(inside0 - position.feeGrowthInside0LastX128, position.liquidity, 2 ** 128)
//              0      -          3.45e34                        → panic 0x11
```

Solidity 0.8.24 проверяет переполнение, поэтому это не «мусор в комиссиях», а жёсткий
откат всей транзакции. Позиция запирается: `collect` вызывает `_modifyPosition(..., 0)` и
падает так же, как `burn`.

## Почему это не проявляется у первого LP

У того, кто создал пул, `feeGrowthGlobal` был равен нулю в момент минта. `last = 0`,
`inside = 0`, всё сходится. Ошибка вылезает только у **следующих** LP, которые заводят
**новый диапазон** после того, как пул уже накопил комиссии.

## Условие срабатывания

Нужны все три условия одновременно:

1. в момент минта `tickCurrent >= tickLower` (нижняя граница диапазона не выше текущей цены);
2. нижний тик диапазона **ещё не инициализирован** (вы в этом диапазоне первый);
3. `feeGrowthGlobal != 0` (пул уже успел накопить комиссии).

Если диапазон целиком выше текущей цены (`tickCurrent < tickLower`), `feeGrowthOutside`
остаётся нулём и всё работает. Если тики уже кем-то инициализированы — тоже работает.

## Проверено на цепи

| сценарий | диапазон | результат |
|---|---|---|
| цена внутри, тики свежие, комиссии накоплены | −63270…−63230 | **заперта**: `collect`/`burn` → panic 0x11 (проверено на форке живого пула) |
| цена внутри, тики уже чужие | −63360…−62950 | работает: `collect` 0x0607351b…, `burn` 0x380f88fd… |
| диапазон целиком выше цены, тики свежие | −64000…−63990 | работает: `burn` 0xb318e1fe… |

Запертый минт: `0x047a17dd319c490af7204c04bc9cae4f4dc0ea0fa7755366e49ad39b90516bcc`.
Сохранённое `last` = `34547351093531036828061949710658433` — ровно `feeGrowthGlobal0X128`
на момент минта.

### Насколько это навсегда

В первой редакции этого документа было написано «навсегда, ни при какой цене». При
проверке оказалось, что это **неверно**, и формулировку пришлось исправить.

Разность, которую считает `_modifyPosition`, равна `global_now - 2 * global_mint`, когда
цена внутри диапазона. То есть позиция разблокируется сама, как только глобальная
комиссия превысит **удвоенное** значение на момент минта.

Проверено воспроизведением на дефектном коде (`test/StuckUnlockLocal.t.sol`, удалён после
проверки):

```
global at mint              170141183460469231731687303715884
last0                       170141183460469231731687303715884
fails right after mint?     true
после роста комиссии вдвое  fails after doubling? false
```

Для живой запертой позиции:

```
last0             3.4547e34
global0 сейчас    4.5341e34   (65.6% от порога)
нужно             6.9095e34
```

То есть позиция откроется, когда в пуле наберётся ещё примерно столько же комиссии,
сколько накопилось за всю его историю. На пуле с оборотом в десятки долларов это
месяцы или годы — практически «заперто», но не «навсегда».

Практический вывод не меняется: чинить надо, деньги считать потерянными. Но формулировка
важна — «навсегда» было бы неправдой, а неправда в описании собственной ошибки хуже самой
ошибки.

## Как починено

Внесено в `contracts/SementsulV3.sol`, функция `_modifyPosition`. Идея — пересчитать снимок
комиссии для свежей позиции **после** инициализации тиков:

```solidity
// Свежая позиция — та, у которой ликвидности ещё нет либо она выведена целиком.
bool fresh = position.liquidity == 0 && liquidityDelta > 0;

// ... обновление тиков (_updateTick выставляет lower.feeGrowthOutside = global) ...

// Снимок пересчитывается уже по инициализированным тикам.
if (fresh) {
    (inside0, inside1) = _feeGrowthInside(tickLower, tickUpper, tick);
}

position.feeGrowthInside0LastX128 = inside0;
position.feeGrowthInside1LastX128 = inside1;
```

Почему именно так, а не как в Uniswap. В Uniswap `Position.update` вообще не трогает
`feeGrowthInsideLast` у позиции с нулевой ликвидностью: там снимок остаётся нулевым, и это
корректно, потому что позиция отдельно от «вечных» сборов не существует. У нас структура
одна на всё — и на позицию, и на начисление, — поэтому нулевой снимок означал бы «начислено
всё с начала времён» и дал бы другое переполнение, уже в противоположную сторону.
Пересчёт после инициализации даёт то же поведение, что в Uniswap, и не зависит от истории
пула.

Проверка: `test/StuckPosition.t.sol`, 6 тестов. На дефектном коде падают три из них
(`Panic 0x11`), на исправленном проходят все шесть:

```
FAIL  test_firstMintIntoFreshRangeDoesNotLock   (last snapshotted from stale inside)
FAIL  test_collectWorksAsFeesGrow               (panic 0x11)
FAIL  test_reentryAfterFullExitDoesNotLock      (panic 0x11)
```

Отдельно проверено, что пересчёт не ломает соседние случаи: диапазон целиком выше цены,
повторный вход в уже инициализированный диапазон, пул без накопленных комиссий.

### Что это значило для передеплоя

Правка меняет код пула, а адрес пула зашит в фабрику (она разворачивает пул через
`create2` с солью от пары и тира). Поэтому передеплой был обязателен, и он выполнен:

1. ✅ Развёрнуты новая фабрика V3 и роутер V3 — адреса выше.
2. ⚠️ Старый пул `0x3688726E…` остался с дефектом навсегда: его код неизменяем.
   Он сохранён в `deployments.js` как `wbnbUsdtV3PoolLegacy`, пользоваться им нельзя.
3. ⚠️ Запертую позицию перенести нельзя — ключ считается от владельца и границ
   диапазона, а ликвидность лежит внутри пула.
4. ✅ Рабочая ликвидность выведена из старого пула до переезда и внесена в новый.

`scripts/redeploy-v3.mjs` разворачивает ровно два контракта. Обычный
`scripts/deploy.mjs` для этой задачи не годится: он развернул бы все четыре
контракта и перезаписал бы `deployments.js` целиком, потеряв адрес токена,
пары SEM/WBNB и старого пула.

Порядок переезда описан в `docs/BOT-MIGRATION-TASK.md`; адреса в нём обновлены на новые.

## Что должен сделать бот перед переездом

Бот `lp-ladder` живёт в отдельном репозитории и в этом рабочем каталоге его нет —
правку в него эта сессия не вносила и проверить не могла.

Когда бот будут переключать на Sementsul, в `mintPosition` нужна проверка перед минтом:
если нижний тик диапазона ещё не инициализирован, а в пуле уже накоплены комиссии —
минт не отправлять. Иначе первый же такой минт запрёт позицию. Проверка стоит три
чтения (`ticks(tickLower)`, `feeGrowthGlobal0X128`, `feeGrowthGlobal1X128`) и нужна
только для Sementsul: на PancakeSwap дефекта нет.

Сам бот остаётся на PancakeSwap (`DEX = "pancake"` в `wrangler.toml`), пока пул не
передеплоен.
