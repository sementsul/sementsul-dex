# Индексатор не видел сделок нашего пула

**Статус:** исправлено, тест добавлен.

## Что было видно снаружи

Блок «Последние сделки» на главной либо не показывался, либо показывал чужие
сделки. По нашему пулу USDT/WBNB (`0x37c7702B…`) история была всегда пустой,
хотя обмены через него проходили — например, транзакция
`0xc0150d4c12b2aebdf0a43f7aef44cedeaa3a1d2b82ea98b7efc652e648b8adf9`
на 1 USDT.

Выглядело как «в пуле никто не торгует». На самом деле торговали, но
индексатор эти сделки не находил.

## Причина первая: неверный topic0

Событие `Swap` у нашего пула и у пула Pancake V3 — разные события, хотя
называются одинаково.

```
Pancake V3:  Swap(address sender, int256 amount0, int256 amount1, ...)
             0x19b47279256b2a23a1665c810c8d55a1758940ee09377d4f8d26497a3577dc83

Наш пул:     Swap(address sender, address recipient, int256 amount0, ...)
             0xc42079f94a6350d7e6235f29174924f928cc2ac818eb64fed8004e115fbcca67
```

Разница в одном аргументе — `recipient`. У Pancake его нет, у нас есть, потому
что пул отдаёт токены не тому, кто вызвал `swap`, а тому, кого указали. Хеш
сигнатуры от этого меняется целиком.

В `worker/logic.js` стоял хеш Pancake. Наш пул такое событие не эмитит никогда,
поэтому фильтр отбрасывал всё. Ошибка молчаливая: скрипт отрабатывал без
единой жалобы и просто писал «сделок 0».

## Причина вторая: отрицательный tick читался как положительный

`tick` в событии — это `int24`. В ABI он дополнен знаком до полного 32-байтного
слова, поэтому `-63304` выглядит как

```
0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff08b8
```

Код делал `BigInt('0x' + word)` и получал `1.157920892373162e+77` — то есть
число, которое даже не помещается в разумный диапазон тиков. Настоящий тик
нашего пула около `-63204…-63304`, так что расхождение было не на проценты, а
на 80 порядков.

Это ломало бы не только график: по тику считаются границы позиции и проверка
цены.

## Причина третья: объём всегда ноль

В `parseSwapV3` стояли жёстко заданные `amountIn: 0n` и `amountOut: 0n`.
Даже когда событие находилось, в базу писался нулевой объём, и статистика
показывала нулевой оборот при непустой истории. Суммы теперь берутся из
`amount0`/`amount1` с учётом знака: плюс — пул получил токен, минус — отдал.

## Что исправлено

| Файл | Правка |
|---|---|
| `worker/logic.js` | topic0 заменён на сигнатуру нашего контракта; `tick` читается как `int24` со знаком; `amountIn`/`amountOut` считаются из сумм события |
| `scripts/index.mjs` | разбирает и V2, и V3 (`parseSwapV2 ?? parseSwapV3`); пул по умолчанию — наш `0x37c7702B…` вместо чужого SML/WBNB; `GETLOGS_SPAN` снижен с 45 000 до 9 000; границы блоков округляются до целых |
| `worker/index.js` | пара по умолчанию — наш пул, а не чужой `0xd5394617…` |
| `scripts/test-swap-parsing.mjs` | новый набор: 18 проверок на настоящем логе из транзакции `0xc0150d4c…` |
| `scripts/verify-v3-swap.mjs` | проверка разбора на живой сети по конкретной транзакции |

### Две ошибки, найденные по дороге

**`GETLOGS_SPAN = 45000`.** Комментарий уверял, что publicnode отдаёт 50 000
блоков за запрос. На самом деле лимит — 10 000: 40 000 отвечает «query exceeds
max block range 10000», 50 000 — «exceed maximum block range: 50000». Каждый
запрос гарантированно падал, скрипт молча переключался на обход по receipts и
работал минутами. Со стороны это выглядело как зависание без вывода.

**Дробные номера блоков.** При `DAYS=0.1` выражение `head - DAYS *
BLOCKS_PER_DAY` давало `135791217.6`. Такого блока не существует, `eth_getLogs`
отвечал «Invalid params» — и снова включался медленный обход. Теперь границы
округляются: `Math.ceil` для начала, `Math.floor` для конца.

## Проверка после исправления

Индексатор прогнан по окну 38 315 блоков, где лежат свопы нашего пула:

```
блоки 135772452..135810766 (38315)
логов 11, сделок 7
готово: вставлено 7, 7.8 с
```

Цены в базе — 555.39…561.19 USDT за WBNB, что совпадает с рынком на тот момент.

Направление сверено с цепью по событиям `Transfer`: для каждой из 7 сделок
проверено, в какую сторону реально двигались USDT и WBNB. Расхождений нет.

## Почему тест на это не срабатывал раньше

Не было ни одного теста на разбор логов. Проверялись математика, пулы,
комиссии, база знаний — всё, кроме того места, где данные попадают в базу.

Новый набор строит событие ровно в том виде, в каком его эмитит контракт, и
проверяет, что тик равен `-63304`, суммы не нулевые, а цена сходится с
`sqrtPriceX96`. Я убедился, что тест действительно ловит обе ошибки: если
вернуть старый topic0 — падает одна проверка, если вернуть чтение тика как
`uint256` — падает другая.

## Как проверить сейчас

```bash
node scripts/test-swap-parsing.mjs     # 18 проверок
```

Проверка на живой сети — по конкретной транзакции:

```bash
node scripts/verify-v3-swap.mjs        # разбирает реальный лог из BSC
```
