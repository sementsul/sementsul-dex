# Дефект в задеплоенном пуле: сумма с остатком 1 wei зацикливает swap

Найдено при написании тестов на квотер 2026-11-27. Проверено на реальном
пуле через `eth_call`. Пул `0x37c7702B589c69D1e4f4ad32E19f372ED6780278`
**неизменяем**, поэтому дефект не чинится — его нужно знать и учитывать.

---

## Что происходит

В пуле есть цикл обмена (`contracts/SementsulV3.sol`, строка 638):

```solidity
while (state.amountSpecifiedRemaining != 0 &&
       state.sqrtPriceX96 != sqrtPriceLimitX96) {
    ...
    state.amountSpecifiedRemaining -= int256(step.amountIn + step.feeAmount);  // 666
    ...
}
```

Если на шаге получается `amountIn == 0` и `feeAmount == 0`, то
`amountSpecifiedRemaining` не меняется, а цена уже не может сдвинуться
(округление `uint160`). Условие цикла остаётся истинным навсегда.

Защиты от нулевого прогресса в цикле **нет**: проверок `gasleft()` или
отказа вида `NO_PROGRESS` в контракте не найдено. Транзакция съедает весь
газ и откатывается с `out of gas`.

## Почему `amountIn` выходит нулевым

При точном входе цена пересчитывается так:

```
next = ceil(L·2^96 · sqrtP / (L·2^96 + amount·sqrtP))
```

Для достаточно малого `amount` результат в `uint160` равен исходному
`sqrtP` — сдвига нет. Тогда `getAmount0Delta(next, sqrtP, L)` считает
разницу между одинаковыми числами и даёт `0`. Комиссия от нуля тоже `0`.

## Замерено на реальном пуле

`liquidity = 4509276405385454871807`, tick `-63281`:

| сумма | результат `eth_call` с газом 2 000 000 |
|---|---|
| 1 USDT (`1e18`) | дошёл до оплаты — **норма** |
| **1 USDT + 1 wei** | **исчерпал газ** ← дефект |
| 1 USDT + 2 wei | дошёл до оплаты — норма |
| 0.5 USDT | норма |
| 10 USDT | норма |
| **10 USDT + 1 wei** | **исчерпал газ** ← дефект |

Зависание возникает не только на «крошечных» суммах: **1.000000000000000001
USDT** — вполне осмысленная сумма — попадает в щель.

### Почему это точно цикл, а не другая ошибка

Формулировка «Transaction creation failed» сама по себе неоднозначна: так
RPC может сообщить и о нехватке газа, и о другом сбое. Поэтому проверено
две вещи (`scripts/prove-dust-loop.mjs`).

**Первое: отказ не зависит от лимита газа.**

```
газ    300000  Transaction creation failed.
газ   1000000  Transaction creation failed.
газ   5000000  Transaction creation failed.
газ  20000000  Transaction creation failed.
```

Двадцать миллионов газа — в 25 раз больше обычной транзакции — не помогают.
Обычная ошибка (нет баланса, нет approve) от лимита не зависит так; а
незавершающийся цикл съедает ровно столько, сколько дали.

**Второе: соседние суммы на том же лимите проходят.**

```
1e18-1     дошёл до оплаты (упал на transfer from the zero address)
1e18       дошёл до оплаты
1e18+1     Transaction creation failed  ← только эта
1e18+2     дошёл до оплаты
1e18+3     дошёл до оплаты
```

Отличие ровно в один wei. Если бы дело было в балансе или approve, падали
бы все суммы подряд. Значит причина — в самой сумме, а единственный способ
«упасть на сумме» при исправной оплате — не сойтись в цикле.

## Как часто

Симуляция полного цикла на 5 000 последовательных суммах (L = 1e23,
fee = 500 bps): зависло **2 из 5 000** (~0.04%), на суммах 2001 и 4001 wei.

Но это доля от подряд идущих малых чисел. Для реалистичных сумм:

```
1000000000000000000  → ок (1 шаг)
1000000000000000001  → ЗАВИСАЕТ
1000000000000000002  → ок (1 шаг)
123456789012345678   → ок
999999999999999999   → ок
```

То есть дефект проявляется на суммах вида `X + 1 wei`, и вероятность
попасть зависит от того, какое округление даст конкретная пара
(ликвидность, цена, сумма).

## Насколько это опасно

**Деньги не теряются.** Транзакция откатывается целиком: балансы, цена и
ликвидность остаются прежними. Теряется только газ неудачной транзакции.

**Чужой газ сжечь нельзя.** Пул не тратит больше газа, чем отправитель
выделил своей транзакцией. Это не вектор атаки на других пользователей.

**Реальный риск — в другом:** пользователь или агрегатор отправляет обмен,
платит газ и получает непонятную ошибку вместо результата. Для агрегатора
это ещё и невозможность посчитать маршрут: `eth_call` квотера тоже
упрётся в газ.

## Что сделано

1. **Квотер и роутер не могут обойти дефект** — они вызывают тот же
   `swap`. Поэтому в тестах суммы округляются вниз до кратного `1e6` wei
   (`_safeAmount`), что исключает остаток в 1 wei.
2. **Дефект зафиксирован отдельным тестом** `test_poolDustAmountHangsSwap`
   — он проверяет, что сумма `1e18 + 1` действительно не проходит. Если
   пул когда-нибудь переделают и тест упадёт, это будет поводом перечитать
   документацию, а не поводом радоваться.
3. **Квотер при ошибке пробрасывает исходную причину**, а не возвращает 0:
   агрегатор увидит настоящую ошибку и не построит маршрут по неверной цене.

## Что НЕ делается и почему

**Пул не передеплоивается.** В нём ликвидность, позиции и история. Ради
дефекта, который срабатывает на суммах вида `X + 1 wei` и стоит только
газа, менять адрес пула — несоразмерно. Все ссылки, чарты и on-chain
зеркало указывают на текущий адрес.

**Роутер не ставит нижнюю отсечку вслепую.** Порог зависит от
ликвидности и цены, поэтому «минимальная сумма» не константа. Вместо
догадки квотер честно падает, а вызывающий видит причину.

## Если дефект начнёт мешать

Единственный настоящий способ убрать его — новый пул с исправленным
циклом:

```solidity
// перед уменьшением остатка:
uint256 consumed = step.amountIn + step.feeAmount;
if (consumed == 0) {
    // Сдвига нет и потребления нет — дальше цикл не продвинется.
    // Либо выходим, либо откатываемся с внятной причиной.
    revert('Sementsul: NO_PROGRESS');
}
state.amountSpecifiedRemaining -= int256(consumed);
```

Стоит ли это делать — зависит от того, появится ли объём, на котором
дефект начнёт срабатывать заметно. Сейчас частота ~0.04% на малых суммах
и близка к нулю на крупных.
