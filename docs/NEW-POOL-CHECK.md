## Главная проблема: пул слишком тонкий

```

```

Что это значит в деньгах:

| Сдвиг цены | Сколько надо влить |
|---|---|
| 0.1% | 4.24 USDT |

Бюджет одной ступени в базе — **$219–228**. Перестановка ступени на таком пуле
сдвинет цену на десятки процентов. Поэтому:

- `REF_POOL` **обязан** остаться на Pancake `0x172fcD41…`. Брать цену из нашего
  пула нельзя: бот начнёт принимать решения по цене, которую сам же и сдвинул.
- Проверено, что 5-польный ABI читает и Pancake-пул (оба отдают `sqrtPriceX96` и
  `tick` первыми двумя полями), так что раздельные `POOL` и `REF_POOL` работают.

## Штраф за разворот: свопы и так расходятся по блокам

`send()` ждёт квитанцию, поэтому два свопа подряд физически попадают в разные
блоки. Проверено:

```
блок первого свопа:  136018389
блок второго свопа:  136018413   ← разворот, штрафа нет
```

На случай, когда квитанция не пришла и блок неизвестен, в `swapV3` добавлено
ожидание следующего блока (`lastSwapBlock` + `waitNextBlock`).

## Что уже сделано в боте

- `SEM` переведён на новые адреса (пул `0x37c7702B…`, фабрика `0xc0B597Be…`,
  роутер `0xF98B7f4e…`), все в нижнем регистре.
- Проверка старого пула: если в `POOL` окажется `0x3688726E…`, минт в свежий
  диапазон при непустом global блокируется с понятной ошибкой. В новый пул
  минтить можно любым диапазоном.
- `swapV3` ждёт новый блок между свопами.
- `DEX` пока остаётся `"pancake"` — живая лестница не тронута.

## Почему пока не переключено (устарело — см. ниже)

Лестница на $447 в пул глубиной $69 не влезает: первая же перестановка сдвинет
цену на десятки процентов, а свопы `ensureFunds` на $200 выпотрошат пул.

Варианты, которые надо выбрать осознанно:

1. **Наращивать пул** — довести TVL хотя бы до $5–10 тыс., тогда ступень $220
   будет двигать цену на 2–5%, что уже сопоставимо с текущими ±2% диапазонами.
2. **Уменьшить ступени** — гонять на новом пуле маленькие позиции ($5–20), но
   тогда доход в долларах будет на порядок меньше.
3. **Держать ликвидность у нас, цену брать с Pancake** — работает технически,
   но при перестановке бот всё равно выпотрошит тонкий пул свопами.
4. **Оставить лестницу на Pancake**, а на новом пуле только тестировать.

# Миграция выполнена (2026-11-27)

## Ошибка в моём первом выводе

Я приравнял проскальзывание **свопа** к проскальзыванию **минта**. Это неверно:
`mint` добавляет ликвидность в диапазон по текущей цене, проскальзывания при этом
не возникает вообще. Поэтому «не влезает» было неверным выводом.

Три ступени по $190 заняли **59%** ликвидности пула — пул не «слишком тонкий»,
он стал почти нашим собственным.

## Что реально ограничивает доход: оборот, а не глубина

Замер за одинаковое окно 3 минуты при одинаковом капитале $447:

| Площадка | В сутки | Годовых |
|---|---|---|
| Pancake (было) | $0.75 | 61% |
| Sementsul (стало) | $0.00 | 0% |

На Pancake за окно — 123 свопа на $30 млн. В нашем пуле за всё окно — ноль.
Реальный органический оборот пула: ~$512/сутки против $2.9 млрд у Pancake.

Выбор сделан осознанно: доход падает, но бот работает на своей бирже.
Это цена цели, а не техническое ограничение.

## Как переключали

1. Сняли обе позиции с Pancake, собрали комиссии: $583.2 против $579.3 на входе.
2. Поставили 3 ступени по $190 в новый пул:

3. WBNB докупили через **роутер Pancake**, чтобы не сдвигать свой пул.
4. Записали 3 ключа `keccak256(encodePacked(owner, lower, upper))` в D1,
   старые записи закрыли (`closed = 1`).
5. `DEX = "sementsul"`, деплой.

газ: цена выходит из диапазона почти каждый час, и перестановки по ~$0.09 съедают

1.18e21 при прежней ширине — **концентрация выросла примерно в 10 раз**.

## Честная оговорка про арбитраж

Объём от арбитража — не бесплатный доход: арбитражник забирает у LP ровно то,
что LP теряет на расхождении (LVR). Порог безубыточности для LP = две комиссии
= 0.10%; арбитраж начинает работать только с расхождения ~0.45%. То есть зона,
где арбитраж существует, — ровно та, где он для LP убыточен.

Поэтому рост дохода должен идти за счёт **органического** потока трейдеров,
а не только арбитражного.

# Семь ловушек Sementsul, найденных ревью (2026-11-27)

Проверено по контракту `SementsulV3.sol` и на живой позиции. Пять из семи
оказались реальными дефектами бота, два — уже корректны.

## 1. `POOL_FEE` определяет `TICK_SPACING` — OK, но хрупко

В `chain.js:147` шаг тика выводится из комиссии:
`POOL_FEE === 100 ? 1 : 500 ? 10 : 2500 ? 50 : 200`. Сейчас `POOL_FEE = 500`
(из `SEM.fee`), значит шаг 10 — верно. **Но** при `POOL_FEE = 100` бот взял бы
шаг 1, а пул требует кратность своему `tickSpacing`:

```solidity
require(tickLower % tickSpacing == 0 && tickUpper % tickSpacing == 0, 'Sementsul: TICK_SPACING');
```

Чтение при этом работает (тики читаются в `ticks()`, а `slot0` отдаёт
`tickSpacing` пятым полем), так что поломка всплыла бы только на первой
сделке. Надёжнее брать шаг прямо из `slot0[4]`, а не выводить из комиссии.

## 2. `simulateContract(collect)` врёт — ИСПРАВЛЕНО

Главный дефект. Комиссия читалась как `p[3] + p[5]` (`tokensOwed + pending`),
а на Pancake — через симуляцию `collect`. И то и другое даёт нули, когда
комиссия уже есть:

- `tokensOwed`/`pending` заполняются только в момент обращения к позиции;
- `collect` сначала переносит начисленное в `pending` (`_modifyPosition(...)`),
  затем `_settlePending` отдаёт лишь созревшее, а оно ещё не созрело.

Замер на живой позиции `-63360..-63320`:

| способ | результат |
|---|---|
| по `feeGrowthInside` | **$0.0291** |
| симуляция `collect` | $0 |
| `owed + pending` (как было) | $0 |

Исправлено: добавлена `calcOwedSem`, считающая по `feeGrowthInside` против
снимка `feeGrowthInsideLastX128`. После правки UI показывает $0.0480 вместо $0.

## 3. Пока позицию не трогали, `tokensOwed` и `pending` нулевые — ИСПРАВЛЕНО

То же исправление. Формула (порядок условий легко перепутать — при ошибке
получаются правдоподобные, но абсурдные числа):

```
below = tickNow >= lower ? outside(lower) : global - outside(lower)
above = tickNow <  upper ? outside(upper) : global - outside(upper)
inside = global - below - above
owed = L * (inside - feeGrowthInsideLast) / 2^128
```

## 4. `jitDelayBlocks` живёт в фабрике — ИСПРАВЛЕНО

Было зашито `vestBlocks: 1150`. Значение действительно 1150 (~8.8 мин), но
хранится в фабрике (`SementsulV3._jitDelay()` спрашивает её при каждом
обращении), поэтому может измениться без передеплоя бота. Добавлена
`chain.jitDelayBlocks()` с ABI фабрики.

## 5. Снятие до конца вестинга сжигает `pending` — ИСПРАВЛЕНО

`_modifyPosition`: при `liquidityDelta < 0` и наличии `pending` —

```solidity
if (removed >= gross) { pending0 = 0; pending1 = 0; vestBlock = 0; }
else { pending = pending * (gross - removed) / gross; }
```

Бот звал `decrease` **до** `collect`, то есть снимал 100% и терял всё
незрелое. Порядок исправлен: сначала `collect` (переносит в `pending` и
запускает вестинг), потом `decrease`.

## 6. Раскладки `positions()` разные — УЖЕ КОРРЕКТНО

У NFT-менеджера Pancake 12 полей, у пула Sementsul 8. Обе структуры
начинаются одинаково и **не падают** — просто молча возвращают не то.
В боте это разделено по `SEM_MODE`: своя ветка читает пул, чужая — npm.
Проверено: пул отдаёт ровно 8 полей.

## 7. Снимок комиссии сбрасывается при любом обращении — УЖЕ КОРРЕКТНО

`collect` и `burn` начинаются с `_modifyPosition(..., 0)`, который пишет
`feeGrowthInsideLastX128`. Поэтому проверять комиссию транзакцией нельзя:
она уедет в `pending`. Бот не проверяет — читает view-методами, что и
требуется.

## Что осталось сделать

- Брать `tickSpacing` из `slot0[4]` вместо вывода из `POOL_FEE` (п. 1).
  Сейчас не ломается, но защита дешёвая.
- `pendingUsd`/`lockedUsd` теперь показываются раздельно: первое — уже
  перенесено и ждёт вестинг, второе — ещё живёт в `feeGrowthInside` и
  требует `collect`, чтобы начать созревать.
