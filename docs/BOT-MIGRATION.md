# Перевод бота на наш пул: что нужно знать

Документ для той сессии, которая будет править `lp-ladder`. Здесь собрано всё,
что отличается от PancakeSwap, и все места, где бот сломается молча.

Адреса и факты проверены на цепи BSC (chainId 56) на момент написания.
Всё, что можно перепроверить, перепроверяемо командами в конце.

---

## 1. Главное различие: у нас нет NFT

Это первое, обо что споткнётся любой код, написанный под Pancake.

Pancake V3 (как и Uniswap V3) держит позиции в NFT через контракт
`NonfungiblePositionManager`: `mint` возвращает `tokenId`, позиции перечисляются
через `tokenOfOwnerByIndex`, комиссии собираются `collect(tokenId, ...)`.

У нас **никакого NFT нет**. Позиция — это просто запись в пуле, ключ которой
вычисляется из владельца и границ диапазона:

```
key = keccak256(abi.encodePacked(owner, int24 tickLower, int24 tickUpper))
```

Отсюда все следствия:

| Действие | Pancake | У нас |
|---|---|---|
| Открыть позицию | `npm.mint(params)` → tokenId | `pool.mint(owner, tickLower, tickUpper, liquidity)` |
| Перечислить позиции | `npm.tokenOfOwnerByIndex` | нельзя перечислить; ключ известен только если знаешь диапазон |
| Добавить | `npm.increaseLiquidity(tokenId, ...)` | `pool.mint(...)` с теми же тиками |
| Убрать | `npm.decreaseLiquidity(tokenId, ...)` | `pool.burn(tickLower, tickUpper, liquidity)` |
| Собрать комиссии | `npm.collect(tokenId, ...)` | `pool.collect(recipient, tickLower, tickUpper, amount0Max, amount1Max)` |
| Узнать позицию | `npm.positions(tokenId)` | `pool.positions(key)` |

**Практическое следствие для бота.** Сейчас он хранит в D1 таблицу
`positions(token_id, level, pct, budget, lower, upper, created_at, closed)`.
`token_id` у нас не существует. Вместо него надо хранить саму тройку
`(owner, lower, upper)` — из неё ключ вычисляется детерминированно, и её всегда
можно восстановить. Заодно отпадает нужда в `tokenOfOwnerByIndex`: у нас
позиция не «принадлежит» по списку, а вычисляется.

Хорошая новость: `tickLower`/`tickUpper` бот уже хранит, так что переход
сводится к тому, чтобы перестать пользоваться `tokenId`.

## 2. Наш пул

```
Адрес:        0x37c7702B589c69D1e4f4ad32E19f372ED6780278
Пара:         token0 = USDT, token1 = WBNB
Комиссия:     500  (0.05%, единицы 1e-6)
Шаг тика:     10
Фабрика:      0xc0b597bee57bba0aae2ce9e73e83217331a24dd9
Роутер V3:    0xf98b7f4effb34dae1f785010ecf71ff796e7fdd1
```

Порядок токенов: **USDT — token0, WBNB — token1**. У Pancake в тире 0.05%
(`0x36696169...`) порядок обратный: WBNB — token0. Если бот где-то зашивал
`zeroForOne` по аналогии, знак перевернётся.

### `slot0()` возвращает 5 полей, а не 7

Это ломает любой код, который декодирует ответ по стандартному ABI Uniswap.

```solidity
// У нас:
function slot0() external view returns (
    uint160 sqrtPriceX96_,
    int24 tick_,
    uint128 liquidity_,
    uint24 fee_,
    int24 tickSpacing_
);

// У Pancake/Uniswap: те же первые три, дальше observation*, unlocked и т.д. — 7 полей
```

Если декодировать наш ответ семью полями, получится ошибка вида
`Position 191 is out of bounds (0 < position < 160)` — именно это и случилось
при первой попытке. **Декодировать надо своим ABI**, взяв его из
`sementsul-dex/src/contracts/artifacts.json` (`SementsulV3Pool.abi`).

Цена в `slot0` — это token1 за token0, то есть **WBNB за 1 USDT**. Привычная
цена (USDT за WBNB) получается обращением:

```
цена_usdt_за_wbnb = 1 / (sqrtPriceX96 / 2**96)**2
```

## 3. Тик → цена

Формула та же, что в Uniswap:

```
price = 1.0001 ** tick          # token1 за token0, то есть WBNB за USDT
```

Для нашего пула:

- tick `-63360` → **564.35** USDT за WBNB (нижний тик = **верхняя** цена)
- tick `-62950` → **541.69** USDT за WBNB (верхний тик = **нижняя** цена)

Обратите внимание: **меньший тик = большая цена USDT за WBNB**. Это не
опечатка, а следствие того, что цена в пуле перевёрнута (в пуле она WBNB за
USDT). Если бот при пересчёте диапазона перепутает концы, позиция встанет
зеркально: вместо диапазона вокруг текущей цены он получит диапазон, в котором
цены нет, и `mint` либо откатится, либо встанет в одну монету.

Шаг тика 10, поэтому `tickLower` и `tickUpper` обязаны быть кратны 10, иначе
`mint` откатится с `Sementsul: TICK`.

## 4. Вход в BNB не работает — это важно

**Обмен нативного BNB через V3-роутер сейчас невозможен.** Не «неудобен», а
падает. Причина в контракте, не в интерфейсе.

Роутер платит за вход через `transferFrom(payer, pool, owed)`, где
`payer = msg.sender`. Когда обмен идёт внутри `multicall` (а он идёт, потому что
BNB надо завернуть в WBNB), `msg.sender` — это пользователь. Роутер пытается
списать WBNB **с пользователя**, хотя тот прислал BNB и WBNB у него нет.

Проверено: если выдать пользователю `approve` на WBNB, тот же calldata проходит.
То есть дело именно в плательщике.

Чинится только правкой контракта: платить с `address(this)`, когда вход был
нативным. Это передеплой роутера и смена адреса — то есть отдельная задача.

**Что делать боту.** Работать в WBNB, не в BNB. Если ему нужен BNB на газ —
держать резерв, а не обменивать. Сейчас в интерфейсе на такой обмен выдаётся
понятная ошибка вместо падающей транзакции.

Выход в BNB (`USDT → BNB`) работает: там своп идёт в WBNB, а потом
`unwrapWBNB` разворачивает его на роутере.

## 5. Роутер: сигнатуры не как у Uniswap

`exactInputSingle` у нас принимает **4 поля**, а не 8:

```solidity
struct ExactInputParams {
    bytes path;              // token(20) + fee(3) + token(20) + ...
    address recipient;
    uint256 amountIn;
    uint256 amountOutMinimum;
}
function exactInputSingle(ExactInputParams memory params, uint256 deadline)
```

У Pancake/Uniswap — восемь отдельных полей (`tokenIn`, `tokenOut`, `fee`,
`recipient`, `deadline`, `amountIn`, `amountOutMinimum`, `sqrtPriceLimitX96`).
Селекторы разные:

```
наш:      0xea7ec9c4   exactInputSingle((bytes,address,uint256,uint256),uint256)
Uniswap:  0x414bf389   exactInputSingle((address,address,uint24,address,uint256,uint256,uint256,uint160))
```

Отправить «унисвопную» calldata нашему роутеру — транзакция упадёт на селекторе.
Это ровно тот баг, который был во фронтенде и который я починил в этой сессии.

Упаковка `path`:

```
path = tokenIn (20 байт) + fee (3 байта, big-endian) + tokenOut (20 байт)
```

Для одного шага длина ровно 43 байта — контракт это проверяет
(`require(params.path.length == 43, 'SementsulRouter: NOT_SINGLE')`).

Другие имена: у нас `refundBNB()` и `unwrapWBNB(uint256,address)`, у Uniswap —
`refundETH()` и `unwrapWETH9`. Селекторы соответственно `0xf37050da` и
`0x9d110e71` против `0x12210e8a` и `0x49404b7c`.

Что **совпадает** с Uniswap и работает как есть: `multicall(bytes[])`,
`exactInput`, `exactOutput`, `exactOutputSingle` (у последних двух та же
4-польная структура).

## 6. Комиссии: вестинг ломает привычный цикл

Это самое важное для бота, потому что меняет экономику всей схемы.

Комиссия не начисляется мгновенно в доступный баланс. Она лежит в `pending` и
становится доступной через `jitDelayBlocks` блоков — своё значение на тир:

| Тир (fee) | Ставка | Задержка, блоков | ≈ времени |
|---|---|---|---|
| 50 | 0.005% | 250 | ~1.9 мин |
| **500** | **0.05%** | **1150** | **~8.6 мин** |
| 2500 | 0.25% | 5150 | ~39 мин |
| 10000 | 1% | 20150 | ~2.5 часа |

Наш пул — тир 500, значит **1150 блоков**.

### Как это выглядит в данных

Комиссия начисляется **лениво**. Пока позицию не тронули (`mint`/`burn`/
`collect`), поля позиции нулевые, хотя `feeGrowthGlobal0X128` уже вырос:

```
positions(key):
  tokensOwed0 = 0     <- ещё не перенесено
  pending0    = 0     <- вестинг ещё не начат
  vestBlock   = 0     <- срок не выставлен
```

Первый `collect` **вернёт 0**. Он только перенесёт начисленное в `pending` и
выставит `vestBlock = block + 1150`. Забрать можно вторым вызовом после этого
блока. Бот, который после свопа сразу зовёт `collect` и ждёт денег, получит
ноль и решит, что сломалось.

Порядок правильный:

1. `collect` (или любой `mint`/`burn`) — фиксирует начисленное в `pending`
2. ждать `vestBlock`
3. `collect` — забирает

### Если снять ликвидность раньше срока

Комиссия в `pending` **сгорает пропорционально снятой доле**. Снял 100% — потерял
всю незрелую комиссию. Это и есть защита от JIT: бот, который входит перед
чужим свопом и выходит сразу после, теряет всё начисленное.

Для честного LP это тоже неудобно: снимая позицию, дождитесь окончания
вестинга, иначе комиссия пропадёт.

### Что это значит для стратегии бота

Сейчас бот переставляет позиции по «лестнице» (`LADDER_COUNT=25`,
`LADDER_STEP=5`). Каждая перестановка — это `burn` + `mint`. Если делать их
чаще, чем раз в 1150 блоков, накопленная комиссия будет сгорать при каждом
`burn`.

Практические варианты:

- **Увеличить шаг лестницы** так, чтобы позиция жила дольше 1150 блоков
- **Не снимать всю ликвидность**: `burn` части доли оставляет пропорциональную
  часть `pending` (контракт считает `pending * keep / gross`)
- **Сначала `collect`, потом ждать, потом `burn`** — но это замедляет бота
- **Смириться**: при узких диапазонах комиссия и так небольшая

## 7. Защита от сэндвича: штраф за разворот

В пуле есть механизм штрафа за разворот направления внутри одного блока
(`reversalPenaltyK` в фабрике). **Сейчас он выключен** (`k = 0`). Если его
включат, `swap` будет списывать больше, чем показывает формула, — бот,
считающий точные суммы заранее, начнёт получать отказы.

Проверять перед работой:

```js
// reversalPenaltyK(uint24 fee) returns (uint24) — именно uint24, не uint256.
const k = await factory.read.reversalPenaltyK([500])
```

Сейчас `0`. Если станет не ноль — суммы входа надо умножать на
`(1 + k * priceImpact)`.

## 8. Приватный RPC: лимит на транзакцию

Транзакции отправляются через `https://bscrpc.pancakeswap.finance` (Pancake MEV
Guard). Это не прихоть: публичный мемпул даёт фронтраннить.

Ограничение, на которое уже наступали:

```
Transaction gas limit too high (cap: 16777216, tx: 28000000)
```

Потолок — **16 777 216** (2²⁴) газа на транзакцию. `eth_estimateGas` иногда
возвращает больше из-за особенностей оценки V3, поэтому в коде есть потолок
`MAX_GAS` и запасной `FALLBACK_GAS`. Если бот отправляет транзакции сам, ему
тоже нужен этот потолок.

## 9. Где бот сломается молча

Список мест, которые не дадут ошибки, но дадут неверный результат:

**Порядок токенов.** У нас USDT = token0. Если бот считает цену как
`token1/token0` по привычке от Pancake, получит обратную величину и будет
принимать решения по неверной цене.

**`slot0` из 5 полей.** Декодирование семью полями даёт либо ошибку, либо
мусор в `liquidity`.

**Комиссия в `pending`.** `collect` возвращает 0, бот считает, что комиссий нет.

**Сгорание при `burn`.** Позиция закрыта, комиссия потеряна — молча, без
события.

**`tokenId` в D1.** У нас его нет. Схему надо менять до первого запуска, иначе
бот запишет мусор.

**Ключ позиции.** `keccak256(abi.encodePacked(owner, int24, int24))` — именно
`encodePacked`, не `encode`. С `encode` ключ не совпадёт, и `positions()`
вернёт нули без всякой ошибки.

## 11. Как проверить, что всё верно

Дымовой тест: собрать calldata и прогнать `eth_call` с подменой состояния, не
отправляя транзакцию.

```js
// Проверка, что обмен проходит и даёт разумную цену.
const out = await client.call({ to: ROUTER, data, account: ME, stateOverride })
```

В репозитории это уже сделано, можно взять как образец:

- `scripts/test-all-v3-swaps.mjs` — проверяет все ветки обмена
- `scripts/check-fees.mjs` — показывает состояние позиции и вестинга
- `scripts/check-router-selectors.mjs` — сверяет селекторы с байткодом роутера
- `scripts/compare-calldata.mjs` — сравнивает сборку calldata с эталоном viem

Ожидаемый результат на момент написания:

```
ok   WBNB -> USDT обычный -> ~55.6 USDT за 0.1 WBNB
ok   USDT -> WBNB обратный
ok   USDT -> BNB нативный выход
ok   BNB -> USDT: честно отказывает
```
