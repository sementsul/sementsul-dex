# Зеркало на IPFS

Копия интерфейса, которую можно открыть без `sementsul.net`: контент лежит на
IPFS, адрес не зависит от регистратора и хостинга.

Документ описывает, что именно ломается при переносе, что уже исправлено и как
проверить копию до публикации.

## Что даёт зеркало, а что нет

**Даёт.** Интерфейс открывается, если основной домен недоступен. Обмен работает
полностью: расчёт маршрута и подпись транзакции выполняются в браузере, а
данные индексатора берутся с `api.sementsul.net`, который живёт отдельно от
Pages.

**Не даёт.** Серверной части на IPFS нет. Это значит:

- `/api/geo` недоступен — проверка юрисдикции не выполняется;
- заголовки безопасности (`CSP`, `X-Frame-Options`) задаёт шлюз, а не
  `public/_headers` — этот файл на IPFS игнорируется;
- нельзя обновить контент по тому же адресу: CID меняется вместе с содержимым.

Первое — самое важное. Санкционный барьер на зеркале **не работает**, и
интерфейс говорит об этом прямо, а не делает вид, что проверка прошла.

## Что уже сделано в коде

Перенос на IPFS ломается на абсолютных путях: `/assets/…` на шлюзе указывает в
корень домена, а контент лежит по `/ipfs/<CID>/…`. Страница открывается, но без
стилей и скриптов.

| Место | Было | Стало |
|---|---|---|
| `vite.config.js` | `base: '/'` | `'./'` при `MIRROR=1`, отдельный `outDir` |
| `src/App.jsx` (лого) | `/sml-256.png` | `${BASE_URL}sml-256.png` |
| `src/lib/compliance.js` (OFAC) | `/sanctions/…` | `${BASE_URL}sanctions/…` |
| `src/lib/indexer.js` | `api.sementsul.net` | без изменений — адрес уже абсолютный |
| `src/lib/useCompliance.js` | молчаливый `null` при сбое | статус `unavailable` + плашка |

Про последнее — отдельно. Раньше при недоступном `/api/geo` возвращался `null`,
`evaluateGeo(null)` давал «не заблокировано», и на зеркале барьер тихо исчезал.
Теперь это отдельное состояние `geoUnavailable`, и вверху страницы висит
предупреждение. Формулировка честная: барьер работает только на `sementsul.net`.

## Сборка

```bash
npm run build:mirror
```

Скрипт собирает `dist-mirror/` с относительными путями и проверяет результат:

- все локальные ссылки в `index.html` относительные;
- нет ссылок от корня домена;
- санкционный список попал в сборку и не пуст;
- в JS нет абсолютных путей к статике;
- адрес API абсолютный;
- запрос `/api/geo` остался относительным.

Последний пункт — не оплошность. Именно провал этого запроса на IPFS включает
плашку. Если сделать его абсолютным, зеркало будет ходить за гео на основной
домен, и тогда барьер неожиданно заработает там, где его не должно быть — а при
недоступности домена снова сломается молча.

## Проверка до публикации

```bash
node scripts/serve-mirror.mjs 8801
```

Сервер отдаёт сборку по подпути `/ipfs/<CID>/`, повторяя поведение шлюза. Открыть
`http://127.0.0.1:8801/` — произойдёт переход на подпуть.

Что должно быть видно:

- страница со стилями, логотипом и списком последних сделок;
- вверху предупреждение о том, что проверка юрисдикции не выполняется;
- в консоли `404` на `/api/geo` — это ожидаемо и не ошибка;
- `200` на `sanctions/ofac-addresses.json` и на `api.sementsul.net/api/trades`.

## Публикация

Зеркало выложено в Pinata и раздаётся **своим воркером**:

**https://api.sementsul.net/mirror/**

CID: `bafybeidlqhwtm3jntjmcloewabi6cx7q3bm3lqd4wrpgjtm64h2onxnbl4`

Перезаливка после правок:

```bash
npm run build:mirror
PINATA_JWT=… node scripts/pin-mirror.mjs --name=sementsul-mirror-vN
# затем обновить MIRROR_CID в worker/index.js и npx wrangler deploy
```

### Почему не публичный шлюз

Проверено на живом зеркале, все варианты отпадают:

| Шлюз | Результат |
|---|---|
| `gateway.pinata.cloud` | **403** — «HTML content cannot be served through the pinata public gateway», только платный dedicated gateway |
| `ipfs.io` | 429 |
| `dweb.link` | 429, плюс Chrome помечает домен как высокого риска |
| `w3s.link`, `nftstorage.link`, `gateway.ipfs.io` | 301/302 → `ipfs.io` → 429 |
| `cloudflare-ipfs.com` | закрыт |
| `4everland.io` | 301 в поддомен, который не отвечает |
| `ipfs.filebase.io` | 200, **но сломан IPv6** |

Последнее особенно коварно. У `ipfs.filebase.io` есть AAAA-запись
`2001:41d0:700:7828::1`, которая не отвечает. Chrome по умолчанию идёт по IPv6
первым и получает `ERR_CONNECTION_CLOSED`, хотя `curl -4` отдаёт 200. Внешне
это выглядит как «ссылка битая», а на деле виноват сломанный IPv6 у чужого
шлюза. Проверить так:

```bash
curl -4 -o /dev/null -w '%{http_code}\n' 'https://ipfs.filebase.io/ipfs/<CID>/'   # 200
curl -6 -o /dev/null -w '%{http_code}\n' 'https://ipfs.filebase.io/ipfs/<CID>/'   # 000
```

Поэтому зеркало раздаёт воркер на своём домене: у Cloudflare IPv4 и IPv6 в
порядке, лимитов публичных шлюзов нет, домен наш.

### DNSLink и поддомен

DNSLink (`_dnslink.поддомен` с `dnslink=/ipfs/<CID>`) гибче, но на проверенных
path-шлюзах (`gateway.pinata.cloud`, `ipfs.io`) такие пути отдавали 403. Для
поддомена надёжнее указывать конкретный CID.

Свой прокси делает поддомен ненужным: `/mirror/` живёт на уже
сертифицированном `api.sementsul.net`. Если понадобится отдельное имя, это
делается обычным CNAME на тот же воркер.

## Обновление

CID новый при каждом изменении: адрес контента — это хеш содержимого. Поэтому
обновление зеркала — это `npm run build:mirror`, повторная загрузка и замена
CID в DNS или в панели шлюза.

## Ограничения, которые не обойти

**CSP на шлюзе.** `public/_headers` на IPFS не применяется. Шлюз ставит свои
заголовки, и повлиять на них нельзя. Это не ухудшает безопасность контрактов:
ключи не покидают кошелёк, подпись происходит в браузере.

**Плашка про юрисдикцию видна всем.** На зеркале её видят и те, кому барьер не
адресован. Это осознанный выбор: лучше явное предупреждение, чем тихое
отключение проверки.

**Зеркало не заменяет основной сайт.** Оно для доступности, а не для обхода
ограничений. Условия использования действуют и на зеркале.
